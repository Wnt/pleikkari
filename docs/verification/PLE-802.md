# PLE-802: the Go's pad input off the main looper

`stream_go_vr_input_thread` is off by default. It has a Settings switch (Go only), a
flag-gate allowlist entry, and a `DataStore` route (`CodeSwitchDataStoreTest` covers it).

## What the arm does

PLE-746 measured the dispatch of an injected key to the app (KeyEvent → app) at 9.3 ms p50 and
13.9 ms p95, of which the app's own work is 0.7 ms. The main looper also carries the decoder's
frame signal by default, so a key can queue behind video work.

**Why not an `InputQueue`.** `StreamVrActivity` is a `ComponentActivity`, so it has no native
activity's queue. `Window.takeInputQueue` would not help anyway:

* `ViewRootImpl.setView` builds the window's `WindowInputEventReceiver` on `Looper.myLooper()`,
  the main thread for an activity's window.
* With an input queue, `ViewRootImpl` still reads each event there first. Its
  `NativePreIme`/`NativePostIme` stages only then forward it to the queue.

A window's events arrive on the looper of the thread that added the window. So the arm adds a
second window from a thread of its own.

**The window.** While a session streams into the cinema, `InputThreadWindow` (a `GoPadInput`
`HandlerThread`, `THREAD_PRIORITY_DISPLAY`) adds a 1x1 `TYPE_APPLICATION_PANEL` sub-window of the
activity's:

* **Alpha 0:** SurfaceFlinger has no layer to composite.
* **Focusable:** it gets the focus, so every key and joystick event arrives on `GoPadInput`.
* **Not touchable, not touch-modal:** touches still reach the activity.
* **`FLAG_ALT_FOCUSABLE_IM`:** not an IME target, so no key takes a round trip through the
  keyboard's process.

**Routing.**
* On `GoPadInput`, each event goes through the activity's own routing, `routeKey` and `routeMotion`:
  the remote's Back (a long press recentres), the VR menu, then `StreamInput`.
* An event that routing does not take goes back to the main thread, which runs it through the
  activity's window: Activity's `onKeyDown` (a pad's Back leaves), then PhoneWindow (volume and
  media keys).
* The main thread's answer is returned to the input dispatcher, so fallback keys behave as before.
* If the main thread does not answer within 1 s, the event counts as unhandled.
* The window goes when the cinema stops. Its `GoPadInput` log lines are `Input window added`,
  `has the focus` and `removed`.

**Thread safety:**
* **`StreamInput`.** One lock covers the four partial states, the display rotation, the coalescing
  flag, and every controller-state callback: each change and the state it sends form one
  critical section. So a state is never torn and a change is never lost. The state sent last is
  computed after the last change, whichever thread made it.
* **`Session`.** `setControllerState` and the native free are exclusive, so a key on `GoPadInput`
  cannot reach a freed session. `StreamSession.session` is volatile.
* **The lib.** `chiaki_session_set_controller_state` already takes `feedback_sender_mutex`.
* **The VR UI.** `VrUiHost.key`/`motion`/`recentre` only read volatile fields and post to
  `GoVrUi`. `StreamVrActivity.cinema` and `backDownMs` are volatile.
* **`libraryFlow`** is null whenever the window runs: a Library launch drops it before its
  session attaches.

**Ordering caveat, at the window's start only:**
* An event the activity took just before the new window had the focus can still be waiting on the
  main looper when a newer one arrives on `GoPadInput`.
* Keys cannot cross over: the input dispatcher cancels a key held down in the window that loses
  the focus.
* A joystick move can. The stick then shows the older position until the pad's next joystick event.

With coalescing on (`stream_controller_input_coalescing`), the flush still runs on the main
thread's Choreographer. A/B this arm with coalescing off, the default.

## Proven

* **The gate:** `scripts/dev/gate.sh --emulator` printed GATE: PASS on the branch rebased onto
  PLE-801's landing (`639eb52c`), with 315 unit tests.
* **`StreamInputThreadTest`** (Robolectric, SDK 25):
  * The same pad script sends identical controller states, in the same order and with the same
    handled answers, on the main thread and on a `HandlerThread`. The script covers every mapped
    button, the digital and analog triggers, both sticks, the hat, the refused events and
    `releasePad`.
  * With the main thread writing touch states and `releasePad` while the pad thread sends keys and
    joystick events:
    * every change sends exactly one state;
    * no state is torn (each joystick event moves all axes together);
    * the last state sent is the current one.
  * With the lock removed, this second test **fails** with torn states, in every run tried
    (3 of 3).
* **Emulator smoke:** passed (phone path; the arm is off and Go-only).

  (`1KWPH802EW8203`) reported level 6 %, then 5 %, not powered, with VrAlertService holding the

* **A Bluetooth pad is paired but asleep.** An "Xbox Wireless Controller" [LE] is bonded to the Go.

  `dumpsys input` has no gamepad device.

`input keyevent` (`PRESS=key`), the real KeyEvent path: the debug pad broadcast skips Android
input. The input-side stages in `presses.csv` time every press, whether or not the PS5 acts on
it. So the PS5 only needs to be somewhere a Cross press does no harm: High Contrast, as in
PLE-746's README, with an even `PRESSES`. Alternate the arms, one lease per session:

**Acceptance:**
* **The arm runs.** Each `on` session's `probe-lines.txt` has `GoPadInput: Input window has the
  focus`, and its atrace puts the `PLE746 input dispatchKeyEvent` sections on the `GoPadInput`
  thread.
* **Input dispatch.** `input dispatch (event -> app)` and `KeyEvent -> packet sent` p50/p95 on
  `on` against `off`. The KeyEvent time has ms resolution, so compare the distributions over all
  presses.
* **Nothing else moves.** Every press reaches `sent`. VrApi `FPS=72`, `Stale` and the `Cinema
  video:` latched fps are no worse than `off`.
* **By hand, once:**
  * the remote's Back opens the VR menu, and a long press recentres;
  * the menu takes the pad;
  * the headset's volume keys still change the volume.
