# PLE-635: the Oculus Go's video decoder and its Qualcomm low-latency switch

Which hardware decoder Pleikkari uses on the Oculus Go, which low-latency options its Android 7.1
media stack accepts from an app, and what they do to decode time. The consumer is PLE-601
(Oculus Go latency rounds), which A/Bs the result.

## Device and build

* Oculus Go, serial `1KWPH802EW8203`, Wi-Fi ADB `192.168.1.202:5555`, `ro.product.device=pacific`,
  `ro.board.platform=msm8996` (Snapdragon 821), Android 7.1.1 / API 25, fingerprint
  `oculus/vr_pacific/pacific:7.1.1/NGI77B/20008400174500000:user/release-keys`.
* PS5-466 (`192.168.1.164`), reachable per `scripts/dev/ps5-discover.py` before the runs.
* Stream: the app's default profile, 1920x1080 at 60 fps, H.265, target 14.6 Mbps (measured
  10-11 Mbps).

## What the Go exposes

`/system/etc/media_codecs.xml` lists the hardware decoders first, then includes
`media_codecs_google_video.xml`:

| Decoder | Size | Blocks/s | Frame rate | Notes |
|---|---|---|---|---|
| `OMX.qcom.video.decoder.avc` | 64x64-4096x2160 | 1,958,400 | 1-240 | `adaptive-playback`; `vt-low-latency` limit = 1; `vt-max-level` 52 |
| `OMX.qcom.video.decoder.hevc` | 64x64-4096x2160 | 1,958,400 | 1-240 | `adaptive-playback` |
| `OMX.qcom.video.decoder.{avc,hevc}.secure` | | 979,200 | | `secure-playback` required |
| `OMX.google.h264.decoder`, `OMX.google.hevc.decoder` | | | | software |

`media_codecs_performance.xml` measures the Qualcomm HEVC decoder at 216-249 fps for 1920x1080,
and the AVC decoder at 170-191 fps for 1920x1088. There are no `c2.*` codecs on 7.1.
`dumpsys media.player` lists no codec state, and `dumpsys media.codec` is empty on this build.

**What Pleikkari picks:** `AMediaCodec_createDecoderByType("video/hevc")` gives
`OMX.qcom.video.decoder.hevc`. Logcat for every live stream shows
`OMXMaster: makeComponentInstance(OMX.qcom.video.decoder.hevc) in mediacodec process`, then
`MediaCodec: [OMX.qcom.video.decoder.hevc]`. `AMediaCodec_getName` is API 28, so the session log
can only say `Video decoder component: unknown (API < 28)`. The first match for `video/avc` in
the same list is `OMX.qcom.video.decoder.avc`, but no H.264 stream was run live.

Before PLE-635, every Go session configured tier 3 plus the default-path
`operating-rate=960 frame-rate=60` (six operator sessions on 2026-09-27, all the same). The
existing `vendor.qti-ext-dec-picture-order.enable` key never fires on the Go, because it is gated
on a `c2.qti.` component name.

## Which keys reach the decoder on Android 7.1

Read from the Go's own binaries: `/system/lib64/libstagefright.so` (ACodec),
`/vendor/lib64/libavenhancements.so` (Qualcomm's `ExtendedACodec`, which runs in the app process
and logs `ExtendedACodec: setupVideoDecoder()` on every stream start) and
`/vendor/lib{,64}/libOmxVdec.so` (the OMX component in the `media.codec` process). They were
disassembled with the NDK `llvm-objdump`.

| MediaFormat key | Reaches the decoder? | Effect |
|---|---|---|
| `low-latency` (API 30) | no | ACodec 7.1 has no such key; it is silently ignored |
| `vendor.qti-ext-dec-picture-order.enable`, `vendor.qti-ext-dec-low-latency.enable` | no | there is no `vendor.*` extension mapping before Android 8 |
| `frame-rate` | yes | input port frame rate |
| `operating-rate` | yes | `OMX_IndexConfigOperatingRate` → `V4L2_CID_MPEG_VIDC_VIDEO_OPERATING_RATE` (Q16). The driver accepted both 240 and today's 960 (no `codec does not support config operating rate` and no `Failed to set operating rate` in logcat) |
| `priority` | yes | `OMX_IndexConfigPriority` → `V4L2_CID_MPEG_VIDC_VIDEO_PRIORITY`; 0 = realtime |
| `android._num-output-buffers` | yes, but overwritten | ACodec's `setPortBufferNum`, but with a Surface, `configureOutputBuffersFromNativeWindow` recomputes the count from `nBufferCountMin` plus the window's min-undequeued count. Not a knob when decoding to a Surface |
| **`vt-low-latency`** | **yes** | `ExtendedACodec::setupVideoDecoder` (any `OMX.qcom.*` component, any codec) calls `getExtensionIndex("OMX.QTI.index.param.video.LowLatency")` and sets it with `bEnable = value != 0`. The vdec maps that name to index `0x7F00005B`, whose `set_parameter` case logs `Enabling DECODE order`, turns timestamp reordering off and sets V4L2 control `0x992007` to 1 (output order = decode). A failed get or set returns the error and fails the whole configure |
| `thumbnail-mode` | yes | `OMX.QCOM.index.param.video.SyncFrameDecodingMode`: sync frames only. Unusable for streaming |
| `use-arbitrary-mode`, `smooth-streaming`, `prefer-adaptive-playback`, `vpp-*` | yes | not latency knobs (frame-by-frame is already the default: `Decoder will be in frame by frame mode`) |

The vdec also has `OMX_QcomIndexParamVideoDecoderPictureOrder`, but nothing on the 7.1 path
calls it. The Go's `media_codecs.xml` advertises `vt-low-latency` only for the AVC decoder. The
code path does not check the codec, so it applies to both.

## The setting

`stream_decoder_qcom_vt_low_latency` (developer settings: "Qualcomm low-latency decode (Oculus
Go)"). It defaults to off, and it is shown and applied only when `Build.DEVICE == "pacific"`.
When on, the decoder format gets `vt-low-latency=1` at every configure tier, so frames come out in
decode order with no display-order hold. The PS5 stream has no B-frames, so decode order is
display order. If configure fails with the key, the tiers are retried without it. The session
log says `Qualcomm VT low-latency decode requested` and
`AMediaCodec_configure() succeeded ... with vt-low-latency`. The diagnostics overlay shows the
flag `qcom-vt`.

The `Feedback stats:` line (with `stream_feedback_stats_log=true`) now ends with
` | decode mean_ms X p95_ms Y`. That is the per-window mean and p95 of input-queue to
output-dequeue time, so the session log alone carries the decode time.

## Measured on the Go (live PS5-466 stream)

Two 45 s streams on 2026-09-27 at 01:04-01:06 UTC, back to back, on build
`app-ple635-v1.apk` (SHA-256 `e1c843f1…`). The first five stats windows are skipped. The build
had the first version of this ticket's setting: an operating-rate profile (`operating-rate=240`,
the decoder's advertised capacity at 1080p, plus `priority=0`) instead of today's default path
(`operating-rate=960 frame-rate=60`).

| Arm | Decoder config | Windows | Frames | Decode mean | Window means | Window p95 (median / max) |
|---|---|---|---|---|---|---|
| A (today) | tier 3, `frame-rate=60 operating-rate=960` | 37 | 2225 (60.0 fps) | **6.88 ms** | 6.37-7.64 ms | 9.36 / 11.71 ms |
| B | tier 3, `frame-rate=60 operating-rate=240 priority=0` | 34 | 2037 (59.8 fps) | **6.99 ms** | 6.49-7.85 ms | 9.79 / 12.47 ms |

No input or presenter drops occurred in either arm. The operating-rate profile changed nothing,
because today's 960 is already accepted, and priority has its own setting
(`stream_decoder_realtime_priority`). So the profile was replaced by `vt-low-latency`, the one
Qualcomm low-latency option that 7.1 lets an app reach. **The `vt-low-latency` off/on A/B has not
run yet.** From 01:10 UTC the Go was reserved end to end by `resource:go` worker runs
(PLE-650-654), and PLE-635's per-session lease requests never got it again.

## Method notes for PLE-601

* **Starting a stream headlessly on the Oculus TV panel is not solved.** Android 7.1's
  `dumpsys activity <pkg>` searches only the focused stack, which is vrshell's, so it answers
  "no activities match" for an app hosted in Oculus TV's ActivityView. `uiautomator` and
  `input tap` reach only display 0. A TAB/ENTER walk to `playButton` therefore has to be blind,
  and on 7.1 focus order is geometric: the toolbar comes first, then the quality-preset buttons,
  whose ENTER rewrites stream prefs.
* **Display 0 works:**
  1. `am force-stop`, and check that no `fi.madekivi.pleikkari/` ActivityRecord exists on any
     display (an `am start` of a panel-hosted activity crashes SystemUI, PLE-600).
  2. Write the prefs.
  3. `am start -W -n fi.madekivi.pleikkari/.main.MainActivity`.
  4. `uiautomator dump`, then `input tap` on the enabled `playButton` bounds.
  5. Wait for `StreamActivity`.
  6. End the stream with `am force-stop`. A BACK on display 0 arms vrshell's
     `systemux://dialog/exit`, which swallows later launches until one more BACK.

  The decoder, its format and the decode-time metric are the same as on the TV panel. What
  differs is the Surface's consumer.
* A pending `systemux://dialog/exit` shows in logcat as
  `DialogController: showDialog systemux://dialog/exit` right after a launch. One BACK clears it.
