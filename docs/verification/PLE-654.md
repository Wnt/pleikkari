# PLE-654: a live PS5 stream in the native VrApi cinema on the Oculus Go

This note covers three things:
- A live PS5-466 stream played through the real Connect path into `StreamVrActivity`, with nobody in the headset.
- What the cinema does with the decoder's frames.
- One defect that the capture found and this ticket fixed.

The consumers are PLE-601 (Go latency rounds) and PLE-662 (the `go-latency` run on the native path).

## Starting it unattended

This is PLE-635's display-0 recipe with the cinema setting turned on. PLE-643 used the same
route. The script is `PLE-654/go-live.sh`:

1. **Clear the Go:** `am force-stop fi.madekivi.pleikkari`. Then check that no
   `fi.madekivi.pleikkari/` ActivityRecord exists on any display, because an `am start` of
   a panel-hosted activity crashes SystemUI (PLE-600).
2. **Write the prefs:** the owner's prefs plus `stream_go_vr_enabled=true` and
   `stream_feedback_stats_log=true`, and optionally `stream_go_vr_match_60hz` or
   `stream_vr_environment`. They go through `run-as … cp`, and the script reads them back
   with `cmp`.
3. **Start the app:** `am start -W -n fi.madekivi.pleikkari/.main.MainActivity` (display 0).
4. **Press Connect:** `uiautomator dump`, then `input tap` on the enabled `playButton`. In
   all five arms it read "Connect" at `1716,1106`, one second after the start.
   `GoVrSupport.streamIntent` sends Play to `StreamVrActivity`.
5. **Confirm the stream:** `mResumedActivity` and `mCurrentFocus` show `StreamVrActivity`
   within 1-2 s of the tap. After that, send no input at all.
6. **End it:** `am force-stop`, never BACK. The cinema turns BACK into its menu, and on
   display 0 BACK arms vrshell's exit dialog.

It worked in 7 of 7 arms, between 02:04 and 02:29 UTC on 2026-09-27. PLE-623 once saw
vrshell's `ClearActivity` cover a display-0 `MainActivity`; that did not happen here.
Neither a person nor the Oculus TV panel was involved.

### Proven

The streaming path of the native cinema works end to end on the Go:
- The console session connected.
- The Qualcomm decoder output 60 fps into the cinema's `SurfaceTexture`.
- The cinema thread latched those frames into its external-OES texture.
- Every eye frame it submitted drew the video.
- VrApi held the requested 72 Hz or 60 Hz.

### Decoded frames the cinema never shows

At 72 Hz, 3.4-4.6 % of decoded frames (2.1 to 2.8 of 60 per second) never reach the eye
buffer. At 60 Hz, with PLE-636's `stream_go_vr_match_60hz`, it is 8.7-11.5 %, and it varies
more from window to window. This held in all seven arms, across three builds.

Likely mechanism (inferred from AOSP 7.1's `BufferQueue`, not traced on the Go):
1. The cinema loop blocks in `vrapi_SubmitFrame2` once per refresh.
2. It calls `updateTexImage` at most once per iteration, and only after `onFrameAvailable`
   has set its flag through the main looper.
3. The codec's `Surface` and the `SurfaceTexture` are both app-controlled, so the queue can't
   block the producer. A new frame replaces one still waiting (`mDequeueBufferCannotBlock`
   makes queued items droppable), and Java gets no callback for the replaced frame.
4. So whenever decode and network jitter put two decoder outputs inside one refresh slot,
   the older frame is dropped without a trace.

A 72 Hz slot (13.9 ms) is shorter than the 16.7 ms frame interval, so this happens only with
jitter. A 60 Hz slot equals the frame interval, so any phase jitter near the latch point
causes a collision. The phone showed the same effect: `docs/design/DEJITTER.md` D9 found
15-17 % of frames never latched at 60 Hz under immediate release.

**What this means for PLE-601:**
- A 60 Hz arm must be read with the `Cinema video:` line, not only with VrApi's `FPS=` and
  `Stale=`. PLE-643's 60 Hz capture showed 0 stale frames and a 60 fps decoder while it
  was losing about one frame in ten.
- A small queue in front of the latch trades latency for those frames. That is an A/B,
  not a fix.

### The presenter was told 72 Hz at 60 Hz (fixed)

`StreamVrActivity` called `updateDisplayTiming(72.0, 0L)` whatever rate it had asked VrApi
for. In arm B (60 Hz panel) the session log showed the wrong rate:
- `Video presenter vsync period seeded: 13888889 ns (source=panel, 72.00 Hz)`
- `Video presenter disabled mode: … display=72.00 Hz`

It now passes the requested rate. In arms D and G this logs
`16666667 ns (source=panel, 60.00 Hz)` and `display=60.00 Hz`, and arms E and F (72 Hz) are
unchanged.

With today's defaults the presenter is in `disabled` mode (immediate release), so the
wrong rate only mislabelled the logs. Any presenter policy that paces to the display would
have paced to the wrong vsync. This is a defect fix, so it ships unconditional.

### The cinema room on a live stream

Arm C measured the cinema environment with a live PS5 picture:
- `App=` median 8.02 ms.
- 170 stale frames in 56 s (3.0/s, max 26/s).
- VrApi `Early` median 55/s against 72 in the plain arms.

This matches PLE-623's synthetic preview (7.54 ms, 2.5 stale/s). The live decoder and latch
add nothing visible to the room's cost.

`Environment frame: gpu` read 2.40-2.90 ms (median 2.87 ms), even though PLE-651's change
(the timer ends after the whole eye frame) is in this build. It still reads about a third of
VrApi's `App=`, so keep using `App=` for Go GPU cost.

## Not proven

* **Anything seen or heard in the headset:** image quality, judder, tracking, orientation,
  sound and controller mapping. Nobody wore the Go.
* **Entry from the Oculus TV task:** the Library path, where MainActivity is hosted in
  Oculus TV's ActivityView. This route starts `MainActivity` on display 0 instead.
* **Latency:** no latency figure (PLE-601, PLE-662). The dropped-frame mechanism above is
  inferred, not traced.
* **The emulator:** it proves nothing here. The change lives in the `src/vr` source set,
  which only arm64 SDK builds contain.
