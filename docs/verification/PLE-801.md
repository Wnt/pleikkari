# PLE-801: Go cinema latches the decoded frame on the decoder's frame signal (A/B arm, default off)

## What it does

`stream_go_vr_latch_on_signal` is off by default. It has a Settings switch (Go only), a
flag-gate allowlist entry (measurement), and the debug `debug.pleikkari.vr_pacing` item `signal`.
It changes the plain cinema's loop only while that loop runs on VrApi's release (the default,
`stream_go_vr_late_start` off). The loop (`StreamVrActivity.CinemaThread`, `vr-frame-pacing.c`):

1. The previous `vrapi_SubmitFrame2` returned at VrApi's release (a throttled submit), video is
   showing, and no decoded frame is pending.
2. The loop parks (`LockSupport.parkNanos`) until the SurfaceTexture's frame-available listener
   unparks it, or until 7.5 ms before VrApi's next release on PLE-715's grid, whichever comes first.
   The 7.5 ms is `PLEIKKARI_VR_PACING_DEFAULT_BUDGET_NS`, the late start's budget.
3. It latches (`updateTexImage`) and draws at once.

Today's loop latches at step 1 and draws the old frame. A frame decoded while that submit waits
for the release then waits out a whole refresh before its latch (PLE-746: release → latch 8.6 ms
p50, 14.7 ms p95).

**Head-loop guards:**
* The loop waits only right after a throttled submit, never after a late one, and never past a
  release it can still make (`pleikkari_vr_pacing_latch_deadline_ns` returns 0 then).
* If a frame it made wait still comes late, the next frame is held to the budget before the
  release after it: the late start's hold, in `pleikkari_vr_pacing_wake_ns`. Otherwise that frame
  would go through at once in the same refresh, and two submits in one refresh add a refresh of
  VrApi lead (PLE-715), so `Prd` would ratchet up.
* The arm does nothing in a room (as the late start) or under the late start. The late start
  already starts the frame at the arm's deadline, and waking it earlier would lengthen VrApi's
  prediction and undo its hold and drain.

How the three switches combine is in `third_party/ovr_sdk_mobile/README.md` ("Latch on the frame
signal").

**Log line.** With the stats log on, each second's `GoCinema: Frame pacing (…)` line is followed by:

```
GoCinema: Frame pacing latch on signal: W of N frames waited, S woken by a frame, D by the deadline | wait mean/max a/b ms | L waited and came late (next held)
```

The wait counts as the loop's own sleep, so that line's "start to submit" and "start to
predicted" run from the latch. With the setting off, no pacing log line changes.

## Expected effect (a model, not a measurement)

The model:
* a 60 fps stream in the 72 Hz loop (13.924 ms refresh);
* the loop top 0.5 ms after each release;
* every frame shown by the first latch after it arrives;
* the signal delivered at once.

`python3` simulation of 20,000 frames, with arrival jitter of 0 and ±2 ms (both give the same
figures):

| | release → latch p50 / p95 / mean | arrival → release slot, mean |
|---|---|---|
| today's loop | 7.0 / 13.2 / 7.0 ms | 20.4 ms |
| latch on the frame signal | 1.0 / 7.3 / 2.3 ms | 14.5 ms (**−5.9 ms**) |

About 43 % of frames arrive inside the wait window and go out one release (13.9 ms) sooner. The
rest wait as today, but at most the budget. No frame is dropped that today's loop shows.

On the Go the signal adds the listener's hop:
* on the main looper by default, which also dispatches input and the session's LiveData;
* on `GoCinemaFrames` with `stream_go_vr_frame_listener_thread`.

VrApi's lead is not touched, so at lead 1 (the usual `Early` regime) `Prd` should stay at 46 ms.
The risk is the frames drawn at the deadline, with 4.5 ms of work slack instead of about 12. Under
the late start that slack gave 0.4 % late frames (PLE-715). Here, a late frame at lead 1 keeps its
slot, and the hold keeps the lead from growing. `latch_sum.py`'s "waited and came late" count and
VrApi's `Stale`/`Prd` show the cost.

## Proven

* `scripts/dev/gate.sh`: `GATE: PASS` with the Go SDK built in (`Go VrApi: SDK enabled`).
  * Host lib build and ctest; the chiaki-unit case list includes the new
    `/chiaki/vr_frame_pacing/latch_on_signal`.
  * `assembleDebug` and `testDebugUnitTest`.
  * `libpleikkari-vr.so` in the APK exports `VrCinemaNative_latchDeadline`/`latchWaited` and
    `pleikkari_vr_pacing_latch_*` (NDK `llvm-nm`).
* `/chiaki/vr_frame_pacing/latch_on_signal` covers:
  * off → never waits;
  * no deadline before the first frame;
  * the deadline is the budget before the next release, also when VrApi's return is 0.4 ms
    either side of the grid;
  * no wait past the deadline, and none after a late frame;
  * a signalled wait followed by a throttled submit holds nothing;
  * a wait followed by a late frame holds the next one to the budget before the release after it;
  * a late frame that did not wait is today's (no hold);
  * the window counters;
  * the late start never waits.
* `CodeSwitchDataStoreTest` (Robolectric) round-trips every switch Settings adds in code. It found
  that `stream_go_vr_late_start` (PLE-715) and `stream_go_vr_warm_up` (PLE-755) never stored a
  change from Settings: the DataStore had no route for them. That defect is fixed in the same
  branch; without the fix the test fails on `stream_go_vr_late_start`.
