## The defect that was there: the screen missed the runtime's own recentre

With PLE-702's temporary logging, `VRAPI_SYS_STATUS_RECENTER_COUNT` went up between
frames 1 and 2 of every session (113 to 114, 115 to 116; `diag/`, `diag2/`). That is when
VrApi logs `HMT was mounted` and the tracking service `ResetCorrections`. So the runtime re-bases
LOCAL space right after the cinema's first-frame placement (`recenterPending` starts true),
and the screen kept the old space's yaw. In one live void arm on the tip the Go never moved,
yet the screen came out rolled about 90 degrees (`live/shot-void-fp1.png`). For a
face-down Go, a re-base in yaw is a roll of the view. For a person wearing it, the same
re-base puts the screen that far to the side, and the void around it is near-black. The same
happens whenever the runtime recentres mid-stream: a worn Go put back on, or a long press of
the Oculus button.

Fix (`vr-cinema.cpp`, unconditional): read the count every frame (1000 reads took 1.0-1.4 ms
on the Go, `diag2/`) and place the screen again whenever it changes. Each placement logs
`Screen placed at frame N (reason): head yaw Y, pitch P degrees, runtime recentres C[, full pose]`
(the `(reason)` field and the `provisional` suffix came with attempt 2, below).

| preview void, full pose on | mean 46.0, max 247 | `fix/shot-void-fp1.png` |

## Attempt 2: the table pose outlived the pick-up

The runtime-recentre fix does not explain "black **while wearing it**". PLE-668's void-on
logcat (`wt/ple-668/build/ple668/logcat-raw-void-on.txt`) has one `HMT was mounted`, at
10:12:41 Go time (07:12 UTC). That is the stream start, with the Go on the table, and there
is none near the operator's look at 07:16. `go-keepawake.sh` pins the proximity sensor to
"worn", so picking the Go up fires no mount event and no runtime recentre. The screen stayed
level at the yaw of a face-down Go (pitch -87), which says nothing about where the person
holding it faces. The screen could be behind them. Everything around it is near-black by
design: the plain room is black, and the host render of the void at eye level is 5,6,8 at
the zenith to 22,23,35 at the horizon (`android/vr-environment/render-host.sh --check`).

Fix (unconditional): a placement made with the head steeper than 60 degrees is
**provisional**, unless it uses the full pose. Once the head has stayed within 30 degrees of
level for 36 frames (0.5 s at 72 Hz), the screen is placed again at the head's gaze and logged
`(head came level)`. The decision is plain C in
`android/app/src/main/cpp/vr-screen-placement.c`, and chiaki-unit covers it in
`/chiaki/vr_screen_placement` (5 cases). With the provisional rule disabled,
`table_then_worn` and `steep_request` fail.

Build `jonni/ple-702-bisect-…` on the Go, preview only (the PS5 was on the operator's hold,
`build/dispatch/PS5-HOLD`, so there was no stream). Evidence is in

## The guard (workspace repo)

`scripts/dev/go-latency/screen_check.py` fails a native screencap whose every 16x16 cell is
darker than 16. `go_stream.sh --path native` sets `debug.pleikkari.vr_full_pose=1` for the
run and restores it on `stop`. `go_stats.py` prints a `screencap` line. `run.sh` exits 1 for
a `native*` label whose screencap is near-black (`--allow-black-screen` opts out).

## Not proven

Nobody wore the Go. Three things still need a person: the headset view after the fix, the
`(head came level)` placement when the Go is picked up off the table (the Go never left the
table, so only the unit tests exercise it), and a real mount event (not the
`prox_far`/`prox_close` broadcasts) or a long press of the Oculus button. Attempt 2 ran no live
stream, because of the PS5 hold. The live 72 Hz rows above are attempt 1's, on the build
without the provisional rule.
