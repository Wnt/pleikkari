## The defect that was there: the screen missed the runtime's own recentre

With PLE-702's temporary logging, `VRAPI_SYS_STATUS_RECENTER_COUNT` went up between
frames 1 and 2 of every session (113 to 114, 115 to 116; `diag/`, `diag2/`). That is when
VrApi logs `HMT was mounted` and the tracking service `ResetCorrections`. So the runtime re-bases
LOCAL space right after the cinema's first-frame placement (`recenterPending` starts true),
and the screen kept the old space's yaw. In one live void arm on the tip the Go never moved,
yet the screen came out rolled about 90 degrees (`live/shot-void-fp1.png`). For a
face-down Go, a re-base in yaw is a roll of the view. For a person wearing it, the same
re-base puts the screen that far to the side, and the void around it is near-black. The same
happens whenever the runtime recentres mid-stream: a worn Go put back on, or a long press of
the Oculus button.

Fix (`vr-cinema.cpp`, unconditional): read the count every frame (1000 reads took 1.0-1.4 ms
on the Go, `diag2/`) and place the screen again whenever it changes. Each placement logs
`Screen placed at frame N: head yaw Y, pitch P degrees, runtime recentres C[, full pose]`.

## The guard (workspace repo)

`scripts/dev/go-latency/screen_check.py` fails a native screencap whose every 16x16 cell is
darker than 16. `go_stream.sh --path native` sets `debug.pleikkari.vr_full_pose=1` for the
run and restores it on `stop`. `go_stats.py` prints a `screencap` line. `run.sh` exits 1 for
a `native*` label whose screencap is near-black (`--allow-black-screen` opts out).

## Not proven

Nobody wore the Go. The headset view after the fix, a real mount event (not the
`prox_far`/`prox_close` broadcasts) and a long press of the Oculus button still need a
person.
