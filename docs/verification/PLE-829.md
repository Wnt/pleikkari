# PLE-829: the phone's pad input off the main looper

`stream_pad_input_thread` is off by default. It has a Settings switch ("Controller input off the
main thread", next to "Unbuffered gamepad dispatch"), a `DataStore` route and a flag-gate allowlist
entry.

## What the arm does

With it on, `StreamActivity` runs PLE-802's `InputThreadWindow` from `onResume` to `onPause`:

* **The window.** A 1x1 sub-window of the stream's own window, added from a `PadInput`
  `HandlerThread`. It is focusable, not touchable and not an IME target, so the pad's key and
  joystick events arrive on `PadInput`. Touches still reach the activity's window.
* **The routing.** On `PadInput`, `StreamInput` sees each event first, as it does on main today.
* **The hand-back.** An event the stream refuses goes back to main, through the activity's window,
  as if it had arrived there. That covers Back (it leaves the stream), volume, media keys and the
  quit dialog. Main's answer is returned to the input dispatcher.
* **What stays on main:** touch, the on-screen controls, the motion sensors and, with
  `stream_controller_input_coalescing` on, the coalesced flush. `StreamInput` locks its own state
  (PLE-802).
* **PLE-830's flush.** PLE-830's `stream_go_vr_input_thread_flush` moves the flush onto whichever
  looper made the change, so it would move `PadInput`'s too. Only the Go's Settings shows it.
* **The first `onResume`** comes before the stream's window is attached. With no window token yet,
  the window starts once the stream's window is attached.
* **Dialogs and the display-mode popup** take the focus while they are up, as they did from the
  activity's window. The input window gets it back when they close.

Two settings of the window matter only on the phone. Both are off on the Go.

* **`hideSystemBars`.** On Android 11 to 13 the focused window controls the navigation bar
  (`InsetsPolicy.getNavControlTarget` returns `focusedWin`). A focused window that asks for nothing
  would bring the bar back mid-stream. Android 14 gives it to the full-screen activity window while
  that window hides it.
  * The window's view carries `HIDE_NAVIGATION | FULLSCREEN | IMMERSIVE_STICKY` before it is added.
    `ViewRootImpl.setView` reads the legacy flags into the window's requested insets before
    `addToDisplayAsUser`, and `IMMERSIVE_STICKY` becomes `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`.
  * So the window's first request already hides the bars, which a swipe reveals for a moment, as
    the stream's own window has them.
* **`unbufferedJoystick`.** PLE-91's `stream_gamepad_unbuffered` is requested on the activity's
  decor, which stops seeing joystick events once the arm is on. The input window requests it on
  itself, once, on Android 11+.

**Android 14+: off the screen, not alpha 0.**
* **The problem.** PLE-802's window has alpha 0. From Android 14, SurfaceFlinger gives no input to
  a layer that has drawn a buffer at alpha 0: `Layer::canReceiveInput`, and
  `LayerSnapshot::canReceiveInput` in the new frontend, read
  `!isHiddenByPolicy() && (buffer == nullptr || alpha > 0)`. Android 11 to 13 check only
  `!isHiddenByPolicy()`.
* **What that did.** The window never got the focus. On the API 36 emulator, WMS requested it
  ("Blamed PadInput using pending focus request"), but the input dispatcher found no focused window.
  It dropped the key, then raised an ANR that killed the app (`build/ple829/emu-arm/logcat.txt`).
* **The fix.** On Android 14+ the window keeps its alpha and sits off the screen, at y −10000 with
  `FLAG_LAYOUT_NO_LIMITS`. SurfaceFlinger composites nothing outside the display:
  `Output::ensureOutputLayerIfVisible` drops a layer whose draw region, clipped to the display, is
  empty. The window draws nothing anyway.
* **Multi-window.** A multi-window task (DeX freeform) ignores `NO_LIMITS`
  (`WindowLayout.computeFrames`), so the window lands on the display as one transparent pixel.
* **The Go** runs 7.1 and keeps alpha 0.

**The measurement.**
* **The probe.** `stream_input_latency_probe` (code-only, allowlisted) starts PLE-746's
  `LatencyProbe` in `StreamActivity`. It writes presses.csv (KeyEvent → StreamInput → controller
  state → history packet sent) and arms the `PLE746` atrace markers.
* **R3, not Cross.** The KeyEvent stamp follows PLE-803's press mask (`debug.pleikkari.probe_buttons`)
  in native code instead of hard-coding Cross, so the phone times R3, which does nothing in the PS5
  menus (PLE-800).
* **The Go.** Its default mask is Cross, so it is unchanged. A Cross KeyEvent no longer opens a
  stray press when the mask names another button.
* **The atrace marker** is now `PLE746 input key press buttons=0x… event_ns=…` (was
  `… key cross …`). Nothing parses it.

## Proven

* **The gate:** `scripts/dev/gate.sh` printed GATE: PASS on this branch after the rebase onto
  PLE-844's landing `b13b0089`: 335 unit tests, no failures (`build/ple829/gate-3.txt`). Before the
  rebase, `gate.sh --emulator` also passed (`gate-2.txt`).
* **Unit tests:**
  * `InputThreadWindowTest` (Robolectric):
    * The phone's window at SDK 30 has alpha 0 and is on the screen. At SDK 35 it is off the
      screen with its alpha. Both carry the hidden-bar flags before they are added, and the
      unbuffered joystick request.
    * The Go's window has alpha 0, only the activity's flags, and no unbuffered request.
    * A key the stream takes stays on `PadInput`.
    * A key the stream refuses gets main's handling, once, and main's answer is the window's.
    * With the hidden-bar flags dropped, the phone test fails.
  * `XmlSwitchDataStoreTest` round-trips every switch in preferences.xml through `DataStore`. It
    found that PLE-509's `stream_senkusha_fallback_notice` never stored a change. That switch is
    now routed.
  * `latency_probe/press_buttons_mask`: a KeyEvent outside the mask opens no press, and one inside
    it does.
* **Emulator smoke:** `emu.sh smoke` passed with the arm off, on the `--emulator` build of
  `32ecd162`. That is this branch's code before the rebase (`build/ple829/emu-smoke-2.txt`).
* **Emulator, arm on** (`build/ple829/emu_arm_check.sh`, `build/ple829/emu-arm2/`): the debug
  diagnostics preview, with no console.
  * `mCurrentFocus` is the `PadInput` window, which logged "has the focus" 0.3 s after it was added.
  * The HWC layer list has no `PadInput` layer.
  * `key_threads.py` on the Perfetto trace: all 14 key events (5 R3 presses, volume up and Back,
    each down and up) were delivered on `PadInput`. So were PLE-746's `PLE746 input dispatchKeyEvent`
    sections.
  * presses.csv has the 5 R3 presses.
  * The stream refused Back, so it went back to main, and main's handling finished the activity.
  * The emulator is Android 16: it proves the routing, the focus and the off-screen window. It
    proves nothing about latency, the nav bar on Android 11 to 13, or the S22's composition.

## The S22 A/B

**Setup.**
* **Device:** `SM-S908B`, serial `192.168.1.105:5555`, Android 16 (SDK 36), on battery at 65 %.
* **Stream:** to PS5-466 (192.168.1.164), portrait, with the phone's stored prefs. Motion is on by
  default. Coalescing and unbuffered dispatch are off.
* **Console:** its screen stayed on Settings → Accessibility → Display and Sound (`stream_start.png`
  in each session), where R3 does nothing.
* **Sessions:** 2026-09-27, 16:56–17:01 UTC, one Samsung lease each, arms off, on, on, off. Each ran
  `s22-probe.sh`: 40 R3 presses (`input keyevent --duration 80 107`) under a Perfetto trace
  (`trace.cfg`), then Back to leave the stream.
* **One APK for all four:** `app-debug.apk` sha256 `39e89b44d088918a…`, the gate build of `32ecd162`.
  The stored prefs went back after every session.
* **Raw artifacts, outside git:** `build/ple829/s22/{off1,on1,on2,off2}/` holds `session.txt`,
  `presses.csv`, `trace.pftrace`, `logcat.txt`, `surfaceflinger.txt` and screencaps. Summaries are in
  `build/ple829/s22/analysis.txt` and `key-stages.txt`.

**The arm runs on the S22.**
* With it on, `mCurrentFocus` is the `PadInput` window, which logged "has the focus" 31 ms after it
  was added.
* `key_threads.py`: all 80 key events of each on session were delivered on `PadInput`, and so were
  PLE-746's dispatch sections. Every one of each off session's was on main.
* The HWC layer list has the SurfaceView and the stream window only. `PadInput`'s visible region is
  (0,−10000)–(1,−9999), off the screen.
* The screencaps show no navigation or status bar in either arm.
* Back, which the stream refuses, went back to main and left the stream.
* There was no ANR, and every press reached the console as a history packet.

**presses.csv, 80 presses per arm (KeyEvent time has ms resolution):**

| stage | off p50 / p95 / max | on p50 / p95 / max |
| --- | --- | --- |
| input → app (the KeyEvent to StreamInput) | 6.33 / 9.17 / 17.28 ms | 3.82 / 6.48 / 10.70 ms |
| app → controller state | 0.09 / 0.19 / 0.30 ms | 0.10 / 0.22 / 0.57 ms |
| state → history packet sent | 0.21 / 0.41 / 0.53 ms | 0.21 / 0.37 / 0.76 ms |
| input → sent | 6.62 / 9.71 / 18.11 ms | 4.18 / 6.87 / 11.15 ms |

Each session agrees with the others of its arm. Input → app p50 was 6.79 and 6.12 ms for off1 and
off2, and 3.91 and 3.68 ms for on1 and on2.

**Where the 2.5 ms goes.** `key_stages.py` follows each key in the trace, in ns, from
InputDispatcher's send to the stream's dispatch. It matches the key by the input channel's sequence
number. Figures are over 160 key events per arm, down and up:

| stage | off1 / off2 p50 (p95) | on1 / on2 p50 (p95) |
| --- | --- | --- |
| dispatcher → app read | 0.20 / 0.21 (0.73 / 0.90) ms | 0.21 / 0.20 (0.59 / 0.54) ms |
| IME round trip | 2.08 / 1.98 (3.22 / 3.02) ms | none |
| app read → stream | 3.36 / 3.23 (5.04 / 4.56) ms | 0.74 / 0.67 (1.25 / 1.42) ms |
| dispatcher → stream | 3.69 / 3.57 (5.40 / 5.05) ms | 0.99 / 0.91 (1.61 / 1.94) ms |

* **The main looper was not making keys wait.** Dispatcher → app read is 0.2 ms on either thread
  at these settings.
* **The IME round trip is what the arm removes.** The stream's own window is an IME target. With
  the arm off, `ViewRootImpl`'s `ImeInputStage` sends every key to Samsung's keyboard,
  `com.samsung.android.honeyboard`, over its `ClientState` channel, and waits for the answer before
  the stream sees the key. That costs 2 ms p50 and 3 ms p95, plus the hop back onto main.
* **Why the arm skips it.** The input window has `FLAG_ALT_FOCUSABLE_IM`, so it is not an IME
  target.
* **So:** on the S22, most of this arm's gain would also come from making the stream's own window
  not an IME target, on main, with no second window. That is a follow-up.

## Not proven

* **A real Bluetooth pad on the S22.** The S22 has no bonded pad here. Real pads' `KEYCODE_BUTTON_*`
  go through `ImeInputStage` too, so the IME detour should apply, but that was not measured.
* **Joystick motion events.** Only injected KeyEvents were measured. Whether a pad's sticks also
  round-trip through the IME is open.
* **Load.** At these settings the main looper added nothing (0.2 ms). With the diagnostics overlay,
  coalescing, or a busier main thread, the thread itself may matter. With coalescing on, the flush
  runs on main unless PLE-830's `stream_go_vr_input_thread_flush` is set.
* **The navigation bar on Android 11 to 13.** The emulator and the S22 are Android 16, where the
  full-screen activity window keeps the bars. The hidden-bar flags are checked in Robolectric only.
* **DeX and multi-window,** where the window lands on the display as a transparent pixel.
* **The on-screen touch controls** stay on main and were not exercised in these sessions.

## Reproduce

From this worktree, after `scripts/dev/gate.sh`, one Samsung lease per arm:

```sh
for arm in off on on off; do
  n=$((n+1))
  /home/wnt/gta6/scripts/dev/device.py run PLE-829 -- \
    bash docs/verification/PLE-829/s22-probe.sh $arm$n android/app/build/outputs/apk/debug/app-debug.apk $arm 40
done
python3 docs/verification/PLE-829/analyze.py build/ple829/s22/{off1,on2,on3,off4}
$PERFETTO_PY docs/verification/PLE-829/key_threads.py build/ple829/s22/on2/trace.pftrace
$PERFETTO_PY docs/verification/PLE-829/key_stages.py build/ple829/s22/*/trace.pftrace
```

`$PERFETTO_PY` is a Python with the `perfetto` package, such as the ab harness venv
(`build/dispatch/ple-5/venv/bin/python` in the workspace).

**Only the first arm installs.** A later arm skips the backup and the install when the phone already
has the APK byte for byte, so it takes about a minute.

**Queue timing.** While other rounds cycle the Samsung, a wait longer than the 10-minute tool limit
loses the queue place. `run-arm.sh` joins only when nobody else is waiting, and `DEADLINE` stops a
late grant from starting a session it cannot finish.
