Go serial `1KWPH802EW8203` (`192.168.1.202:5555`), debug build with SDK 1.35.0, the debug
preview (`--ez vr_cinema_preview true`, no console), `debug.pleikkari.vr_full_pose=1` so the Go

`MainActivity` (its VR home). Artifacts are outside git in `/home/wnt/gta6/build/ple-722/go-s<N>/`:
logcat, screencaps, `session.txt`, `plain-screen-check.txt`.

## What the sessions found

| Session | Result |
| --- | --- |
| `go-s1` | The UI program failed to link (`uniform int mode` is highp in the vertex stage and mediump in the fragment stage). The cinema fell back to the strip menu, as designed. `input gamepad keyevent K` is refused by Android 7.1's `input` |
| `go-s2` | Linked. `KEYCODE_MENU` opened the menu, and the same key's release closed it 14 ms later |
| `go-s3` | The menu, laser, reticle, hover, pad focus, stats panel and room pick all worked, but the right eye lost the picture while a panel was open. The UI pass left its program bound, and the plain screen binds its own only once, before the eye loop. The GL error that left behind then failed the Void room's build (`GL error 0x502 after init`) |
| `go-s4` | Everything fixed. The evidence below |

The shaders are in `android/app/src/vr/cpp/vr-ui-shaders.h`. Compiling and linking them through
Mesa on CT950 (surfaceless EGL, GLES 3.2) reproduces `go-s1`'s link error exactly, and passes
with the fix.

## `go-s4`: the head loop with the menu open (plain room, GPU 315 MHz throughout)

`windows.py` reads the app's own VrApi lines (its pid) between logcat marks, about 35 lines a
window:

| Window | FPS | Prd | Stale (median, mean) | TW | App | LCnt |
| --- | ---: | ---: | --- | ---: | ---: | ---: |
| Menu closed | 72 | 46 ms | 0, 0.00 | 1.69 ms | 1.65 ms | 1 |
| Menu open, idle | 72 | 32 ms | 0, 0.03 | 2.29 ms | 1.77 ms | 2 |
| Menu open, pointer moving (debug ray, 2.5 targets a second) | 72 | 32 ms | 0, 0.00 | 2.29 ms | 1.79 ms | 2 |

Against the §10.9 budget:

- FPS is unchanged.
- Stale is within +0.2 of the closed window.
- `TW=` is +0.6 ms for the menu layer, inside +0.8 ms.
- `App=` is +0.12 to +0.14 ms, inside +0.3 ms.
- LCnt is 1 closed and 2 open.

`Prd` moved from 46 to 32 ms whenever a second layer was up, in `go-s3` and `go-s4` alike. That
is VrApi leaving its every-frame `Early` regime (PLE-715's subject), not a cost.

The `GoVrUi` thread's redraws took 5 to 11 ms each (mean about 8 ms, under 1 ms of it in
`unlockCanvasAndPost`). The first draw after start took 21 to 35 ms. This is over §10.9's
3 ms target, but it runs off the head loop, which showed no stale frames from it.

## Answers to vr-ui.md §11

- **Eye FOV:** `Suggested eye FOV 90.0 x 90.0 degrees`.
- **Gamepad injection:** `input gamepad keyevent KEYCODE_X` fails on the Go's Android 7.1 with
  "Invalid arguments for command: keyevent". `input gamepad keyevent KEYCODE_X KEYCODE_UNKNOWN`
  delivers `KEYCODE_X` with the gamepad source.
- **Screencaps:** a display-0 screencap does include the compositor's cylinder layers.
- **Canvas into a VrApi Surface swapchain:** it works with `lockHardwareCanvas`. The orientation
  is upright with the SDK sample's cylinder texture matrix, and premultiplied alpha composes
  correctly.
- **Long Back:** not tested; nobody pressed the remote.
