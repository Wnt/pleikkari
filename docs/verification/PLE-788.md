# PLE-788: Opus MediaCodec failure mid-stream recovers (S22 Ultra)

Device: Galaxy S22 Ultra, serial R3CT30WLVFV, debug APK from this branch (sha256 ba4f6cb2d038…),
streaming PS5-466 over the LAN, 2026-09-27 18:58 phone time. Script: `PLE-788/session.sh`.

Fault: `adb shell setprop debug.chiaki.audio_fail 1` (then `2`), which makes the audio
output thread call `AMediaCodec_stop` on the live codec (commit b306e531).

Result, from `PLE-788/logcat.txt` (pid 18534):

| time | line |
|---|---|
| 18:58:27.540 | `Audio Output started Oboe stream` (stream start) |
| 18:58:44.066 | `Injecting an Audio Decoder failure (debug.chiaki.audio_fail=1)` |
| 18:58:44.071 | `AMediaCodec for Audio Decoder failed with -10000, stopping output` |
| 18:58:44.080 | `Re-creating Audio Decoder after an output error` |
| 18:58:44.357 | `Audio Output started Oboe stream` |
| 18:58:59.057 | second injection, **from a new output thread** (tid 18766, the first was 18710) |
| 18:58:59.076 | `Re-creating Audio Decoder after an output error` |
| 18:58:59.375 | `Audio Output started Oboe stream` |

Audio comes back: the injection check only runs after 50 decoded output buffers,
so the second injection firing on the re-created decoder's thread proves that
decoder was producing PCM again. `PLE-788/audioflinger.txt` shows an AudioTrack for
the app added at 18:58:44.343 and removed at 18:58:59.117, then another added at
18:58:59.360 and still active at capture time. The stream never quit.

Side effect: each re-create is followed by a burst of 16-20 `Audio Output Buffer
Overflow!` within ~0.3 s. The input that queued up during the ~0.28 s re-open is
dropped. This is the expected ratchet, not a failure.

Not proven: audible audio (nobody listened), and the Oculus Go / Oculus TV scenario
from PLE-661. The Go was not used.
