# PLE-698: per-frame latency through the Go's native cinema, in software

## What was built

With the stats log on (`stream_feedback_stats_log`), the native VrApi cinema times every video
frame on `CLOCK_MONOTONIC` at four points:
* **(a) arrival:** chiaki completes the frame (`frame_ready_time_us`);
* **(b) decoded:** the presenter dequeues the decoder's output buffer;
* **(c) latched:** the cinema's `updateTexImage`;
* **(d) submitted:** its `vrapi_SubmitFrame2` call, with that frame's `vrapi_GetPredictedDisplayTime`.

`chiaki-jni` logs one `Cinema latency:` line per second (tag `Chiaki`, and the session log
during a stream). It gives counts (decoded, latched, shown, replaced before latch, unmatched)
and p50/p95/max/mean in ms for these stages:
* arrival→decoded;
* decoded→latched;
* latched→submitted;
* submitted→predicted photon;
* the total, arrival→predicted photon.

Frames are joined by their SurfaceTexture buffer timestamp. `scripts/dev/go-latency/go_stats.py`
parses the line, and `run.sh` reports it (workspace branch `ple-698`). See
`third_party/ovr_sdk_mobile/README.md` for details.

## Results (31 one-second windows each, the first skipped)

| ms, p50 / p95 / max        | 72 Hz            | 60 Hz (`stream_go_vr_match_60hz`) |
|----------------------------|------------------|-----------------------------------|
| latched→submitted          | 1.9 / 2.3 / 10.4 | 1.9 / 2.5 / 3.8                   |
| submitted→predicted photon | 30.5 / 30.9 / 31.3 | 53.8 / 54.3 / 54.6              |
| latched→predicted photon (sum of p50s) | 32.4 | 55.7                              |
| VrApi `Prd=` p50 (its own line)        | 32   | 56                                |
| VrApi `Early` per second               | 0    | 60 (every frame)                  |
| frames latched / shown / unmatched     | 1080 / 1080 / 1080 | 902 / 902 / 902         |

* **The clocks agree.** Both runs log `GoCinema: VrApi clock minus CLOCK_MONOTONIC: 0.001 ms`.
  VrApi's own `Prd=` covers frame start to predicted display, and it matches latched→photon
  within 0.4 ms in both regimes. The fixture test `test_recorded_preview_runs` pins this within
  1 ms.
* **The cinema's own work is small.** Latch to `vrapi_SubmitFrame2` takes 1.9 ms (p95 2.3-2.5 ms).
  The rest of the on-device path after the latch belongs to VrApi's pipeline.
* **60 Hz ran in VrApi's "early" regime and costs 23 ms more after the latch.** At 72 Hz the
  preview ran `Early=0`, `Prd=32ms`. At 60 Hz every frame was `Early` and `Prd=56ms`, which is 3.4
  refreshes instead of 2.3. The same two regimes are in the earlier captures
  (`build/captures/ple654/run*`). PLE-654's live 72 Hz arms ran mostly `Early=72` at 46-47 ms
  (A, E, most of F), and its live 60 Hz arms (B, D, G) ran `Early=60` at 55-56 ms. So a live
  72 Hz stream is usually one refresh (about 14 ms) later after the latch than this preview's
  72 Hz. The live figures will show which regime each arm ran in.
* **The preview's picture is not 60 fps.** The cinema latched 35.9 fps at 72 Hz and 29.9 fps at
  60 Hz. `PreviewPicture.post()` skips a render loop whenever less than 1/60 s has passed, so it
  posts every other loop. The latch-to-photon stages do not depend on that rate.

## Not proven

* arrival→decoded, decoded→latched, arrival→predicted photon, and the replaced-before-latch count
  on a live PS5-466 stream, at 72 Hz and at 60 Hz. The PS5 hold stopped all of these.
* Whether the decoder's buffer timestamp survives to `SurfaceTexture.getTimestamp()` on the Go
  (the join key). The host tests cover the join. Only a live stream shows `unmatched 0`.
